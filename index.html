Working integration · Flagship

HubTrack Pro

Odoo and Google Sheets integration for inventory movement monitoring and reconciliation across multiple hubs.

Demo with simulated data coming soon
The problem
Inventory movements across multiple hubs and counterpart locations were recorded in Odoo, but extracting, organizing, classifying, and analyzing them took repetitive manual work. The challenge was making the data useful for operational monitoring, not just retrieving it.
The solution
Inventory movement records are pulled directly from Odoo into a structured Google Sheets environment, classified as incoming, outgoing, or internal, and mapped to the correct hubs and counterparts to support analysis and reconciliation.
Technology
Odoo v17 · Odoo JSON-RPC API · Google Apps Script · Google Sheets (ARRAYFORMULA, MAP, FILTER, LAMBDA) · AI-assisted development
My role
I defined the operational requirements and made the key design decisions: Odoo as the source of truth, Apps Script for API extraction, Sheets for analysis, and a separate hub master table for mapping. I set the IN / OUT / INT / IGNORE classification, separated raw data from reference data and calculations, and chose chunked extraction for large volumes. AI tools helped draft and debug the code and formulas. I supplied the business context, evaluated outputs, caught incorrect results, and directed the revisions.
How I validated it
Tested against a live Odoo v17 environment: authentication, record retrieval, chunked extraction, and hub mapping all worked. The validation dataset held 17,051 classified records. When formulas returned wrong results, such as date-based calculations covering all history instead of the requested period, I inspected the underlying fields and refined the logic.
What it demonstrates
Turning a real operational problem into system requirements, designing an API-based data workflow, directing and checking AI-assisted code, and improving a solution through iterative testing.

  • 1,780INT
  • 60IGNORE

A public demo will use simulated data only. No production data, credentials, or proprietary source code is published here.

Working Colab application

DR Scanner App

A guided Google Colab app that finds Delivery Receipts inside ZIP and 7Z archives, reads each DR number with OCR, then sorts and renames the files.

Screenshots coming soon
  1. Extract images
  2. Pre-scan for DRs
  3. OCR and rename
  4. Review flagged
  5. Dedupe and check
  6. Export
The problem
Delivery Receipt images arrive bundled in ZIP and 7Z archives, mixed with other images. Each receipt has to be identified, named by its DR number, de-duplicated, and checked against a Google Sheet.
The solution
A 12-step notebook with one input: the Drive folder path. It extracts the images, sets aside anything that isn't a Delivery Receipt (fuel delivery receipts included), reads each DR number with OCR, and renames the files. Only doubtful reads go to a human, in a review Google Sheet.
Technology
Python · Google Colab · Tesseract OCR (pytesseract) · OpenCV · NumPy · zipfile and py7zr · Google Drive · Google Sheets via gspread and the Sheets API · pandas · openpyxl · ipywidgets
My role
I designed and built the app end to end using AI-assisted development, including the processing rules and the review workflow. A read is accepted and renamed only when it is exactly seven digits plus "A" and at or above a minimum prefix I set. Everything else is flagged with the scanner's read, a suggested fix where one is obvious, and the reason.
Safeguards built in
Steps 6 and 7 resume where they stopped after a disconnect. Corrections open in preview-only mode first. Nothing is overwritten (duplicates get a suffix), and deleting files requires typing DELETE.
What it demonstrates
Designing a multi-stage document-processing pipeline, combining OCR with rule-based validation, keeping a human in the loop for uncertain cases, integrating Drive and Sheets, and making a technical tool usable by non-technical people.
  • Nearly 30,000images processed in total
  • Nearly 20,000in a single batch
